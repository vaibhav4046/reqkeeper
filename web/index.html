Fig. 2 — the load-bearing idea

An invoice is an identity.

Every Request invoice carries a canonical request id and a 16-character payment reference embedded in the calldata. That is a stable obligation identity issued by an external system. It survives a payer wallet change, an API-key rotation, a re-import, regenerated calldata, and the 24-hour replay expiry.

We did not invent an identity scheme. Request already ships one.

// three identities, all derived from persisted state —
// no clock, no randomness, no generated text
obligation = sha256(ns.length:ns:id.length:id)
plan       = sha256(canonicalJson(approvedBytes))
step       = sha256(obligation:plan:stepIndex)

Settlement needs two independent signals: a chain receipt read directly via eth_getTransactionReceipt, and Request’s own hasBeenPaid. A confirmed receipt alone cannot mark anything paid. A provider status string never can.

C23 and C24 are the thesis: the send count does not move across a replay. 16 of 22 refusals happen before any provider write at all.

C24 found a real bug in this codebase. A plan still inside its TTL, whose provider idempotency cache had lapsed, re-entered dispatch, reused the same attempt row, called execute() again — and the provider, having forgotten the key, paid a second time. The guard now sits on firstSendAt, and C24 exists so it cannot regress.

What this does not do.

  1. Duplicate protection is deployment-scoped. It cannot stop an independent wallet, another deployment, or a human paying the invoice out of band.
  2. No semantic dedup across request ids. Two Request ids may name the same real-world invoice. Not detected.
  3. Revocation is not an onchain undo. Already-broadcast work completes.
  4. The audit trail is tamper-evident, not tamper-proof. The same database administrator can rewrite it. It is not blockchain evidence.
  5. No prompt-injection detection. A guarded signer enforces a declarative policy. It does not detect injection and does not claim to.
  6. Approval fatigue is real and unsolved. Measured across 11,429 reviews over seven months, approval rates drift 30.1% → 36.8% while inline comments fall 22%. This design reduces prompt count rather than pretending a per-action queue is safe.
  7. The live leg has not run. Creating a Request invoice needs a credential obtainable only by signing in a browser. Every harness row is tagged FIXTURE. None is labelled live, and none will be until a real Sepolia hash exists.
