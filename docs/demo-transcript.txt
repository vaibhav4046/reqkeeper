ReqKeeper — exactly-once settlement of Request Network obligations

  An agent retries. That is what agent harnesses do.
  When the thing being retried moves money, a retry is a second payment.

  KeeperHub owns reliability within a run.
  Nothing owned obligation identity across runs. That is this.

  3. A human decides. Separately.   [FIXTURE]
──────────────────────────────────────────────────────────────────────────

  Approval is written by scripts/approve.ts, which the MCP server cannot invoke.
  It does not accept a plan hash — it recomputes one from the invoice and refuses
  if that disagrees with what the agent reserved:

      REFUSED: the plan reserved for this obligation is not the plan these
               arguments describe.

  An approval flow that trusts the proposer's summary of its own proposal
  is not an approval flow.

  human approval recorded.

  agent calls settle_obligation    -> RECONCILIATION_PENDING
  physical sends                   : 1

  It stops at RECONCILIATION_PENDING, not SETTLED, and that is the point: the
  fixture chain in this section reports the payment as unseen, so the evidence
  does not yet agree. SETTLED needs an independent receipt AND the source's own
  verdict. A provider saying "completed" is never enough on its own.

  10 more calls, same approved plan:
  physical sends                   : 1

  Still one. The money moved exactly once.

  5. The same protocol, 38 times, against real money   [LIVE]
──────────────────────────────────────────────────────────────────────────

  Every invoice below is a real Request Network invoice on Sepolia, paid through
  KeeperHub, then dispatched a second time through the same function.

  rows                          : 83
  behaved as specified          : 83/83
  real payments                 : 38
  physical sends, total         : 38
  refusals before any send      : 45/45

  Sends equal settled obligations exactly. Not one replay moved money.

  A sample, first four rows, transaction hashes as recorded:

    L001  SETTLED            sends 1  0xb90a0771858581547abe
    L002  ALREADY_SETTLED    sends 0  no send
    L003  SETTLED            sends 1  0x62911d69c66da1c47085
    L004  ALREADY_SETTLED    sends 0  no send

  The odd rows paid. The even rows are the same obligation asked to pay again,
  and every one of them refused at zero sends. That is the product.

  None of the above has to be taken on trust. Reading three of those payment
  references back off Sepolia now, through a public RPC, no credentials:

    L001  on chain: true  amount 1000000000000000000  0xb90a0771858581547a
    L003  on chain: true  amount 1000000000000000000  0x62911d69c66da1c470
    L005  on chain: true  amount 1000000000000000000  0x006ebc9218ef93d8d0

  npm run verify:live does this for all 38, and checks that every refusal row
  really has no transaction. It needs no API key.
