Why Request Network

    
The invoice is the idempotency key. Every Request invoice carries a
      canonical request id and a payment reference embedded in the calldata: a stable
      obligation identity issued by an external system. It survives a wallet change, a key
      rotation, a re-import, regenerated calldata, and the 24-hour replay expiry. We did not
      invent an identity scheme.

    
And the loop closes without fabrication. Pay with the reference embedded and Request's
      own detection flips the invoice to paid. SETTLED requires both an
      independently read receipt and the source's own verdict.

  


  
  

    
The approved bytes are
not the signed bytes

    
Request hands you finished calldata. KeeperHub will not send finished
      calldata. Whatever bridges that is where a payment can quietly change meaning.


    
Probed, not assumed

    
contract-call, data      -> HTTP 400 {"error":"Missing required field","field":"functionName"}
contract-call, callData  -> HTTP 400 {"error":"Missing required field","field":"functionName"}
raw route                -> HTTP 400 {"error":"Invalid action type: raw"}
transaction route        -> HTTP 400 {"error":"Invalid action type: transaction"}

    
The only write surface is (contractAddress, functionName, functionArgs),
      re-encoded on KeeperHub's side against an ABI it resolves itself. So between "the human
      approved these bytes" and "the signer signed these bytes" sits a decode, a transport,
      and a re-encode performed by the execution platform.

The named call survives only as an inner payload: a 65-byte signature, then the

What ReqKeeper does about it

    
Decode the approved calldata, re-encode it locally, dispatch only on a byte-identical
      match. Anything else refuses before a single network call.

    

      

        
Smuggled variantRefusal

        
          
trailing bytes appended after the argumentscalldata_mismatch

          
a selector not on the allowlistselector_not_allowed

          
dirty high bytes packed above an addresscalldata_mismatch

        
      

    

    
The codec refuses every type it does not implement. One that silently
      mis-encodes an argument is worse than none, because it breaks the byte-comparison meant
      to catch exactly that. Its correctness is checked against KeeperHub's own
      encoder output, captured from a live revert payload: two independent
      implementations, same 260 bytes.

      Request invoices on Sepolia; every settled one carries a transaction hash you can look

Four things about that MCP server, each found by probing it

    
    
      
  1. The handshake is sequential. A tools/call before
        notifications/initialized fails with -32003 Session not
        initialized.
    2. 
      
  2. Authentication failure does not look like one. A rejected key still returns
        HTTP 200 on initialize, just with no
        mcp-session-id header. The 401 arrives on the next call, so absence of
        the header is the only reliable signal.
    3. 
      
  3. The session id rotates. An expired-but-in-grace token is silently re-minted and
        returned in a rewritten header, so the newest response wins.
    4. 
      
  4. simulate is compared with === true. The string
        "true" does not dry-run: it signs and broadcasts.
    5. 
    

    
All four are reported upstream rather than only worked around. The
      calldata-passthrough limitation is the subject of a filed issue, and the idempotency
      disposition defect is an open pull request against their staging branch.

  


  
  

    
What the agent cannot do

    
An MCP server over stdio, five tools, and one deliberate omission.

There is no approve tool. Not disabled, not
      behind a permission flag — the capability is absent from the protocol surface. An
      agent connected to this server cannot, by any sequence of calls, authorise money to
      move. The test suite asserts the absence, so adding one breaks the build.

The approval flow does not trust the proposer

    
scripts/approve.ts does not accept a plan hash. It recomputes one from
      the invoice facts you type and compares it against the plan the agent reserved:

    
REFUSED: the plan reserved for this obligation is not the plan these arguments describe.
  reserved by : be7830f4d60c3e9f9a409faf680d51840a93ff8a55922a4e72a9470c3d0a579b
  you typed   : 7fbdadaff7d772ad7f73659f15bce30eb94b03a3b383cb9bdeeeaa34bd76e032

    
An approval flow that trusts the proposer's own summary of what it proposed is not an
      approval flow. That is why the CLI takes the invoice rather than an id.


    
Honest limits

    
    
      
  • Duplicate protection is deployment-scoped. It cannot stop an independent wallet or a human paying the invoice out of band.
    • 
      
  • No semantic dedup across request ids. Two ids may mean the same real-world invoice.
    • 
      
  • Revocation is not an onchain undo. Already-broadcast work completes.
    • 
      
  • The audit trail is tamper-evident, not tamper-proof. It is not blockchain evidence and is not described as such.
    • 
      
  • No prompt-injection detection. A guarded signer enforces a declarative policy; it does not detect injection.
    • 
      
  • The live payee is a burner keypair, not a counterparty, so no third party has confirmed receipt.
    • 
      
  • Sepolia only. Mainnet is disabled in code, deliberately.
